# Core Design — 핵심 게임 기획

> Project Unorder의 코어 시스템 기획. **왜 이렇게 만드는가**를 기록한다.
> 코드 구조 매핑은 문서 하단 §7, 시스템 구조는 [../architecture/](../architecture/README.md).

## 1. 한 줄 요약
두 플레이어(**Order**·**Unorder**)가 **턴제**로 보스의 **탄막**과 싸우는 2D 액션 로그라이크.
게임 전반을 **Rule 시스템**이 규정하며, 룰의 활성화가 플레이 규칙 자체를 바꾼다.

## 2. 두 플레이어 (Dual Character)

| | **Order** | **Unorder** |
|---|---|---|
| 조작 | 키보드 | 마우스(드래그) |
| 역할 | **탄막 회피** | **탄막 제어** |
| 체력 | 있음 (피격 시 파괴) | **없음 = 기본 무적** |
| 이동 | 초기 자유 → 룰로 **제한 영역** 내 한정 | 드래그 조작 |

- `PlayerType { Order = 0, Unorder = 1 }` — 이미 코드에 존재.
- **핵심 비대칭**: 데미지를 받는 주체는 Order 뿐. Unorder는 죽지 않는다 — **단, Rule이 이 전제를 깬다(§3).**

## 3. Rule 시스템 (게임의 최상위 규칙) ★

게임 플레이에 **가장 크게 영향을 주는 시스템**. 특정 룰이 활성화되면 기본 규칙이 뒤집힌다.

### 3.1 성격 — 보스별 애드혹 룰
- 룰은 고정된 카탈로그가 아니라 **보스마다 그때그때 다양하게 추가**해서 쓴다.
- 기획에 따라 **온갖 변칙적인 룰**이 들어올 수 있다. → 무엇이 룰이 될지 미리 알 수 없다.
- ⚠️ **이 프로젝트의 위험 특성**: 룰의 개입 지점이 사방으로 뻗을 수 있어, **가능한 한 많은 지점에 확장성·수정 가능성을 열어두는 것**이 설계의 최우선 제약이다.

### 3.2 확장성 설계 원칙 (필수)
- 룰은 **플러그인처럼 추가/제거**할 수 있어야 하며, 기존 룰이나 코어 루프를 수정하지 않고 새 룰을 붙일 수 있어야 한다.
- 룰이 건드릴 수 있는 대상(플레이어 상태·이동·체력·턴·탄막·보스 등)은 **직접 결합 대신 이벤트/인터페이스로 개입점을 노출**한다.
- "한 보스 전용의 일회성 변칙 룰"도 코어를 오염시키지 않고 격리되도록 한다.
- 흐름: `RuleObserver`(활성/조건 감지) → `RuleManager`(구독·중재) → 대상에 효과 적용.

### 3.3 예시 룰
- **Unorder 체력 부여 룰**: 무적이던 Unorder에 체력이 생겨 **탄막에 파괴될 수 있는 상태**가 된다.
- **영역 제약 룰**: Order의 자유 이동을 막고 **제한된 영역 안에서만** 움직이게 한다. (튜토리얼의 첫 학습 지점, `RULE_BoxLimit`)
- **턴 제거 룰**: 턴제 전투에서 **플레이어의 턴을 없앨 수 있다** — 회피에만 집중해야 하는 국면.
> 위는 예시일 뿐, 실제 룰 목록은 보스 기획에 따라 계속 늘어난다.

### 3.4 폐기된 이전 기획 (참고)
- 과거엔 **보스마다 하나의 룰을 지키고 있고, 플레이어가 그 룰을 의도적으로 위반하도록 유도했을 때 보스가 피해를 입는** 시스템을 기획했었다.
- **너무 비직관적 + 구현 난이도 과다**로 폐기됨.
- 코드의 `RULE_LifeTime`은 이 폐기된 기획의 잔재로 추정 → **제거 대상**(§8-2).

## 4. Unorder 탄막 제어 (드래그 기믹)

1. 마우스 **드래그로 적 탄막을 선택** (`DragZone`, 최대 선택 수 제한).
2. 선택된 탄막에 능력 적용 — **유저 옵션 설정에 따라 능력이 달라질 수 있음**(모듈형).
3. **기본 능력**: 선택 탄 **감속 → 최종 정지**.
4. 정지된 탄은 **흡수**되어 **플레이어 턴의 공격 Point**로 전환된다.

> 회피(Order)와 자원 생성(Unorder)이 동시에 굴러가며, 회피의 산물이 곧 공격 자원이 되는 순환 구조.

## 5. 턴제 전투 흐름

```
[보스 턴] 공격 패턴 진행
     │  패턴 종료 & 플레이어 생존?
     ├─ No  → 게임오버
     └─ Yes → [플레이어 턴]
                 └ 모은 Point로 공격 / 특수행동
                 └ 종료 → 다시 [보스 턴]
※ 특정 Rule 활성 시 [플레이어 턴]이 제거되어 보스 턴만 반복될 수 있음
```

- **보스 턴**: 보스 공격 패턴(`BossAttackPatternSO`) 진행. 이 동안 Order는 회피, Unorder는 탄 흡수로 Point 축적.
- **플레이어 턴**: 축적한 Point 소비 → 보스 공격 또는 특수행동.

## 6. 첫 튜토리얼 전개 (오프닝 시퀀스)

1. Order **자유 이동** 체험.
2. **최초 제약** 발동 → 제한 영역 밖으로 나갈 수 없음을 **학습**시킴.
3. 곧바로 **보스 등장**, 패턴 몇 번 회피.
4. **Unorder 해금** → 드래그 탄막 제어 가능 → 본격 전투 진입.

## 8. 열린 질문 (기획 확정 필요)

### 해소됨 (결정 완료)
- ✅ **RuleManager 정본 = `RuleSystem/RuleManager.cs`.** 빈 `GameSystem/RuleManager.cs`는 삭제 완료.
- ✅ **`RULE_LifeTime` = 폐기된 이전 기획(§3.4)의 잔재** → `RuleObserver.cs`에서 제거 완료.

### 미결 (구현 전 결정 필요)
기획을 그대로 옮기며 아래는 **명세가 비어 있어** 구현 전 결정이 필요합니다:

1. **턴 전환 트리거** — 보스 턴 종료 판정 기준은? (패턴 큐 소진 / 타이머 / HP 임계?) `TurnManager`가 무엇을 보고 턴을 넘기나.
2. **Point 규칙** — 탄 1개 흡수 = 몇 Point? 상한/소멸(턴 넘기면 리셋?) 여부. 공격별 Point 코스트.
3. **Unorder 체력 룰의 발동/해제 조건** — 어떤 이벤트로 켜지고 꺼지나. 체력 수치·회복 여부.
4. **드래그 "유저 옵션 능력"의 범위** — 감속 외 어떤 능력들이 있고 어디서 설정하나(런 중 / 메타 진행).
5. **Rule 개입점 인터페이스 설계** — §3.2 확장성을 위해 룰이 붙을 표준 훅(이벤트/인터페이스) 형태를 어떻게 정할지. (아키텍처 과제)

> 위 항목이 정해지면 이 문서와 [../architecture/](../architecture/README.md)를 함께 갱신한다.
